Production Engineering

Shipping code is the start, not the end. Production engineering covers deployments, incident management, disaster recovery, and the practices that separate companies with 99.99% uptime from those with weekly outages.

⏱ 65 min read 🎯 All Levels 🚀 Deploy & SRE practices

Deployment Strategies

StrategyHowRollback SpeedRiskBest For
Rolling UpdateReplace instances one by one, new version gradually takes overModerate (re-roll)Low-MediumKubernetes default, stateless services
Blue-GreenTwo identical environments. Switch load balancer from blue (old) to green (new)Instant (flip LB back)Low (instant rollback)Critical services, zero-downtime requirement
Canary ReleaseSend 1-5% of traffic to new version. Monitor. Gradually increase to 100%Fast (reroute traffic)Very Low (small blast radius)High-risk changes, large user base
A/B TestingRoute specific users to different versions based on rulesFastLowFeature experiments, product validation
RecreateKill all old instances, deploy all new. Brief downtimeN/A — requires redeployHighDev/staging, low-traffic services
 
# Kubernetes: canary deployment with traffic splitting
---
# Stable deployment (95% traffic)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-stable
spec:
  replicas: 19   # 19 pods = 95% of traffic (assuming equal distribution)
  selector:
    matchLabels:
      app: api
      track: stable
  template:
    metadata:
      labels: { app: api, track: stable }
    spec:
      containers:
      - name: api
        image: myapp:1.2
---
# Canary deployment (5% traffic)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-canary
spec:
  replicas: 1   # 1 pod = ~5% of traffic
  selector:
    matchLabels:
      app: api
      track: canary
  template:
    metadata:
      labels: { app: api, track: canary }
    spec:
      containers:
      - name: api
        image: myapp:1.3  # new version
---
# Single Service routes to BOTH (label selector matches both)
apiVersion: v1
kind: Service
metadata:
  name: api-service
spec:
  selector:
    app: api   # matches both stable AND canary pods

Feature Flags

Feature flags decouple deployment from release. Deploy code anytime; turn features on/off without redeploy. Used by every major tech company.

// Feature flags with LaunchDarkly (or open-source Unleash/Flagsmith)
import LaunchDarkly from 'launchdarkly-node-server-sdk';

const ldClient = LaunchDarkly.init(process.env.LD_SDK_KEY);

async function handleCheckout(user: User, cart: Cart) {
  const userContext = {
    kind: 'user',
    key: user.id,
    email: user.email,
    country: user.country,
    isPremium: user.isPremium,
  };

  // Gradual rollout: returns true for X% of users
  const useNewCheckout = await ldClient.variation(
    'new-checkout-flow', userContext, false  // false = default if flag missing
  );

  if (useNewCheckout) {
    return newCheckoutFlow(user, cart);
  }
  return legacyCheckoutFlow(user, cart);
}

// Types of flags:
// Kill switch:   instantly disable a broken feature without redeploy
// % rollout:     1% → 5% → 25% → 100% gradual release
// User segment:  only for beta users, employees, specific countries
// A/B test:      50/50 split to measure impact

Health Checks & Readiness

# Kubernetes health probes — critical for zero-downtime deploys
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
      - name: api
        livenessProbe:        # if fails → restart container
          httpGet:
            path: /health/live
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 10
          failureThreshold: 3
        readinessProbe:       # if fails → remove from load balancer (no traffic)
          httpGet:
            path: /health/ready
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 5

---
# Health endpoint implementation
@app.get("/health/live")
async def liveness():
    # Simple: is the process alive?
    return {"status": "ok"}

@app.get("/health/ready")
async def readiness():
    # Check all dependencies
    checks = {
        "db": await check_db_connection(),
        "redis": await check_redis_connection(),
        "kafka": check_kafka_connection(),
    }
    all_healthy = all(checks.values())
    status_code = 200 if all_healthy else 503
    return JSONResponse({"status": "ready" if all_healthy else "not ready", "checks": checks}, status_code)

Incident Management

1
Detect — Alert fires (PagerDuty/OpsGenie). On-call engineer acknowledges within SLA. Incident declared if P1/P2 severity
2
Communicate — Create incident channel (#incident-2025-01-15). Notify stakeholders. Update status page (customers)
3
Mitigate — Roll back bad deploy, disable feature flag, scale up capacity, failover to DR region. Restore service first, investigate second
4
Resolve — Service restored. Document timeline in incident record. Assign follow-up action items
5
Postmortem — Blameless RCA. 5 Whys analysis. Preventive action items tracked to completion. Share learnings across org
💡 Blameless Postmortems: Google's SRE culture: postmortems focus on system and process failures, not human errors. People are trying to do their best. The goal is to learn and prevent recurrence — not to assign blame. This creates psychological safety which leads to more honest incident reports.

Disaster Recovery

MetricMeaningTarget
RTO (Recovery Time Objective)Max acceptable downtime after a disasterCritical systems: <1hr. Most: <4hr
RPO (Recovery Point Objective)Max acceptable data loss (how old can restored data be?)Financial: 0 (synchronous replication). Most: <15min
MTTR (Mean Time To Recovery)Average time to restore service after an incidentBest-in-class: <30min for P1
MTBF (Mean Time Between Failures)Average time between failuresHigher is better. Measure and trend over time
