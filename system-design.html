System Design Cases

Walk through 8 real-world system designs the way senior engineers do it — clarify requirements, estimate scale, choose components, handle failure modes, and trade off consistency for availability. These are the exact cases that come up at FAANG interviews.

⏱ 120 min read 🎯 Senior → Principal 💼 Interview Critical 🏢 8 Real Systems

The DESIGN Framework

Before jumping into any system design, follow a structured approach. Interviewers (and architects) evaluate your thinking process more than your answer. Use this framework consistently.

1

Clarify Requirements (5 min)

Scope the problem. Functional requirements (what the system does) and non-functional requirements (scale, latency, consistency, availability). Ask: how many users? read-heavy or write-heavy? global or single-region?

2

Estimate Scale (5 min)

Back-of-envelope calculations. QPS, storage, bandwidth. These drive your technology choices. 1M DAU × 10 requests/day = ~116 QPS. 1TB/day storage = ~11.5 GB/sec write throughput.

3

High-Level Design (10 min)

Draw the boxes: clients, load balancers, web servers, services, databases, caches, queues. Identify the core data flow for the 2–3 most important use cases.

4

Deep Dive (20 min)

Pick 2–3 components to design in detail. Database schema, API design, sharding strategy, caching layer, consistency model. Go where the interviewer leads.

5

Identify Bottlenecks (5 min)

Single points of failure, hot-spot keys, thundering herd, N+1 queries. Propose solutions: replication, sharding, circuit breakers, rate limiting.

📏
Back-of-Envelope Numbers to Memorize

Memory: L1 cache ~1ns, L2 ~10ns, RAM ~100ns, SSD ~100μs, HDD ~10ms, cross-datacenter ~150ms. Storage: 1 char = 1B, 1 photo ~300KB, 1 video min ~50MB. Read/write: MySQL can handle ~5K QPS single node; Redis ~100K QPS; Cassandra ~50K writes/sec per node.

Design a URL Shortener (Bit.ly)

Requirements

Functional

  • Given a long URL, return a 7-char short URL
  • Redirect short URL → long URL
  • Custom aliases (optional)
  • Link expiry (optional)
  • Click analytics

Non-Functional

  • 100M URLs created/day
  • 10:1 read:write ratio → 1B redirects/day
  • Redirect P99 < 10ms
  • System should be highly available (99.99%)
  • URLs should not be guessable

Scale Estimates

Write QPS: 100M / 86400 ≈ 1,160 writes/sec. Read QPS: 1B / 86400 ≈ 11,600 reads/sec. Storage: 100M/day × 365 × 10yr = 365B URLs. At 500 bytes/URL → ~183 TB.

Short URL Generation

MD5/SHA256 the long URL → take first 7 chars of base62 encoding. Problem: collisions when different URLs produce same prefix. Solution: append a counter or user ID to the input before hashing.

Python
import hashlib, base64

def shorten(long_url: str, salt: str = "") -> str:
    h = hashlib.md5((long_url + salt).encode()).digest()
    encoded = base64.urlsafe_b64encode(h).decode()
    return encoded[:7]  # First 7 chars = 62^7 = 3.5T unique URLs

Auto-incrementing ID from a database (e.g. 123456789) converted to base62. Simpler, no collisions, but requires a centralized ID generator. Use Twitter Snowflake or a distributed counter service.

Python
CHARS = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def to_base62(n: int) -> str:
    if n == 0: return "0"
    result = []
    while n:
        result.append(CHARS[n % 62])
        n //= 62
    return "".join(reversed(result))

# ID 1000000 → "4c92" (4-char), ID 3.5T → 7-char max

Hot Key Problem

A viral tweet with a short URL can generate millions of requests/sec to a single key. Solution: local in-memory cache in each web server (store top 1000 most-read URLs in process memory). This eliminates Redis traffic entirely for hot URLs.

Design WhatsApp (Messaging at Scale)

Scale

2B users, 100B messages/day, 60% delivered in <1 second. Multi-device delivery, group chats (256 members), read receipts, end-to-end encryption.

Core Challenge: Message Delivery

1

Sender → Server

Client maintains a persistent WebSocket connection to a Chat Server. Message is sent over this connection. Server assigns a global sequence ID using Snowflake.

2

Server → Recipient

If recipient is online, their Chat Server receives the message via internal Pub/Sub (Kafka topic per user). If offline, message stored in message store with TTL of 30 days; push notification sent.

3

Delivery Receipt Flow

Server sends ACK to sender after storing. Recipient sends "delivered" receipt when message arrives on device. "Read" receipt when user opens the conversation.

Database Design

EntityStorageWhy
User profilesPostgreSQLStrong consistency, relational
MessagesCassandraWrite-heavy, time-series, partition by (user_id, month)
Undelivered msgsRedis (TTL)Fast fanout, auto-expire
Media (photos/video)S3 + CDNBlob storage, global edge delivery
Group membershipPostgreSQLRelational, joins needed
Presence (online/offline)RedisEphemeral, sub-second TTL

Group Messages

Naive approach: fan-out to all group members on write (write amplification for 256-member groups). Better: fan-out on read — store one copy of the message, each member fetches on request. WhatsApp uses a hybrid: small groups fan-out on write, large groups fan-out on read.

🔐
End-to-End Encryption

WhatsApp uses the Signal Protocol. Each device has a public/private key pair. Sender encrypts with recipient's public key — the server never sees plaintext. For groups, each message is encrypted once per recipient (no group key to leak).

Streaming (Read Path)

Adaptive Bitrate Streaming (ABR): video is split into 2-4 second segments. Client monitors bandwidth and switches quality per segment. Netflix uses a proprietary ABR algorithm trained on 300TB of playback data to predict the right bitrate before bandwidth drops.

Recommendation System

Netflix saves ~$1B/year in reduced churn via recommendations. The algorithm factors: watch history, ratings, similar users (collaborative filtering), time of day, device type. Netflix runs 250+ A/B tests at any given time to optimize the algorithm.

Design Uber (Ride Sharing)

Core Challenges

  • Location updates: 14M active drivers sending GPS coordinates every 4 seconds → 3.5M writes/sec at peak
  • Matching: find nearest available driver to rider in <1 second
  • Surge pricing: real-time supply/demand calculation by geohash cell

Geospatial Indexing

Uber divides the world into geohash cells. A geohash is a string where longer = more specific location. Nearby locations share a common prefix. This allows range queries on a 1D string (B-tree) to find nearby drivers efficiently.

Python - Geohash lookup
# Precision 6 = ~1.2km × 0.6km cell
import geohash

def find_nearby_drivers(lat, lon, radius_km=2):
    cell = geohash.encode(lat, lon, precision=6)
    neighbors = geohash.neighbors(cell)  # 8 surrounding cells
    cells_to_check = [cell] + neighbors
    # Query Redis: SMEMBERS driver:{geohash} for each cell
    drivers = []
    for gh in cells_to_check:
        drivers.extend(redis.smembers(f"driver:{gh}"))
    return drivers

The Thundering Herd: New Year's Eve

At midnight on NYE, millions of users request rides simultaneously. Surge pricing isn't just about profit — it's a load-shedding mechanism. Higher prices reduce demand, giving the matching engine time to catch up. Uber pre-scales infrastructure 10× before large events using historical data.

Design Instagram Feed

Scale

2B users, 100M photos/day uploaded, 500M daily active users view feed. A single celebrity (200M followers) posting a photo triggers 200M feed updates — this is the celebrity problem.

Feed Generation: Push vs Pull

Push (Fan-out on Write)

  • When user posts, write to all followers' feed tables
  • Feed read is instant (pre-computed)
  • Works great for normal users (300 followers)
  • Problem: celebrity with 200M followers = 200M writes

Pull (Fan-out on Read)

  • On feed request, fetch posts from all followed accounts
  • No write amplification
  • Problem: reading 1000 accounts' latest posts = 1000 DB queries
  • Slow feed load, especially if accounts post frequently

Instagram's solution: Hybrid. Regular users use push (fan-out on write). Celebrities use pull (fan-out on read). A user following both regular and celebrity accounts gets a merged feed — pre-computed posts from regular accounts merged at read time with recent celebrity posts.

Feed Ranking

Instagram doesn't show posts in reverse-chronological order. It uses a ranking model trained on engagement signals: likes, comments, shares, watch time. Features include: recency, relationship strength (do you DM each other?), content type preference.

Distributed Rate Limiting with Redis

Lua Script (atomic in Redis)
-- Token bucket in Redis (atomic Lua for race-condition safety)
local key = KEYS[1]
local capacity = tonumber(ARGV[1])  -- max tokens
local rate = tonumber(ARGV[2])      -- tokens per second
local now = tonumber(ARGV[3])       -- current timestamp (ms)

local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(bucket[1]) or capacity
local last_refill = tonumber(bucket[2]) or now

-- Refill tokens based on elapsed time
local elapsed = (now - last_refill) / 1000
tokens = math.min(capacity, tokens + elapsed * rate)

if tokens >= 1 then
  redis.call('HMSET', key, 'tokens', tokens - 1, 'last_refill', now)
  redis.call('EXPIRE', key, 3600)
  return 1  -- allowed
else
  return 0  -- rate limited
end

Multi-Tier Rate Limiting

Production systems use multiple tiers: IP-level (100 req/min), user-level (1000 req/min), API key level (custom). Rules stored in Redis, evaluated in order. Stripe uses a combination: free tier gets 25 req/sec, paid gets custom limits per endpoint.

Design a Distributed Cache

Requirements

10M operations/sec, P99 latency < 1ms, support for strings/hashes/lists, cache eviction (LRU), cluster of N nodes with consistent hashing.

Consistent Hashing

Problem with naive key % N: adding/removing nodes remaps almost all keys. Consistent hashing maps both keys and nodes onto a ring (0–2³²). A key is served by the first node clockwise on the ring. Adding a node only remaps keys between the new node and its predecessor.

  Ring (0 → 2^32)

        Node A (hash=10)
       ╱
  ────●──────────────●─────────────●────
      │              │             │
   Key "user:1"   Node B (50)   Node C (80)
   hash=15
   → served by Node B (next clockwise)

  Add Node D at hash=40:
  → Keys between 10 and 40 now move to Node D
  → Only ~25% of keys remapped (not 100%)
Python - Consistent Hash Ring
import hashlib
from sortedcontainers import SortedDict

class ConsistentHashRing:
    def __init__(self, replicas=150):
        self.replicas = replicas  # virtual nodes per server
        self.ring = SortedDict()

    def add_node(self, node: str):
        for i in range(self.replicas):
            h = self._hash(f"{node}:{i}")
            self.ring[h] = node

    def get_node(self, key: str) -> str:
        h = self._hash(key)
        idx = self.ring.bisect_left(h) % len(self.ring)
        return self.ring.values()[idx]

    def _hash(self, val: str) -> int:
        return int(hashlib.md5(val.encode()).hexdigest(), 16)

Eviction Policies

PolicyWhen to UseImplementation
LRU (Least Recently Used)General purpose, temporal localityDoubly linked list + hash map. O(1) get and set.
LFU (Least Frequently Used)Scan-resistant, long-lived hot keysMin-heap by frequency. Better hit rate than LRU for skewed access.
TTL-basedData with known stalenessEach key has expiry. Background sweeper removes expired keys.
RandomWhen all keys are equally importantO(1), very simple. Surprisingly effective at scale.

Design Search Autocomplete (Google Suggest)

Scale

10B queries/day on Google Search. Autocomplete fires on every keystroke — average query is 5 keystrokes → 50B autocomplete requests/day. P99 latency must be < 100ms (feels instant).

Trie Data Structure

A trie stores strings as paths from root to leaf. Each node is a character. Finding all strings starting with "app" requires one traversal to the "app" node, then a DFS of its subtree. Redis doesn't support tries natively, but Elasticsearch and Typesense do.

Python - Trie with top-K
class TrieNode:
    def __init__(self):
        self.children = {}
        self.top_queries = []  # top-10 completions cached at node

class AutocompleteTrie:
    def search(self, prefix: str) -> list:
        node = self.root
        for ch in prefix:
            if ch not in node.children:
                return []
            node = node.children[ch]
        # Each node pre-caches its top-10 → O(prefix_length) lookup
        return node.top_queries

Production Architecture

Google pre-computes top queries per prefix offline (MapReduce over query logs). Trie snapshots are pushed to all edge servers. Updates run every 10–30 minutes. Real-time trending queries are handled separately via a streaming pipeline (Kafka + Flink) that injects into the trie without a full rebuild.
