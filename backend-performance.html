Chapter 4

Backend Performance Engineering

Performance is a feature. Learn how to measure, profile, and optimize backend systems — from understanding latency percentiles to eliminating bottlenecks under production load.

⏱ 70 min read 🎯 Intermediate → Staff 📊 Metrics & Profiling

Latency vs Throughput

Latency is the time to process one request. Throughput is how many requests per second your system handles. They are related but not the same — and optimizing for one can hurt the other.

WHY
Why it matters
Amazon found every 100ms of latency costs 1% in revenue. Google's studies show users abandon pages after 3 seconds
WHAT
What to measure
P50, P95, P99 latency; requests/sec; error rate; CPU/memory utilization; DB query time; external call time
WHERE
Where issues hide
Database queries (most common), N+1 problems, synchronous external calls, serialization, GC pauses, thread starvation
WHO
Who owns it
Backend engineers own app-level perf; SREs own infra-level; DBAs own query perf; the team owns the SLOs collectively
WHEN
When to optimize
After you have metrics showing a real problem. Never optimize speculatively. Measure → identify → fix → re-measure
HOW
How to improve
Profile first. Add caching. Optimize DB queries. Parallelize I/O. Use async. Reduce payload size. CDN for static assets

Percentile Metrics: P50, P95, P99

Averages lie. A single slow request can be hidden in the average. Percentiles show the real experience across your users.

MetricMeaningExampleWhen to alert
P50Median — 50% of requests are faster than this50msRarely; it's your "normal"
P7575% of requests complete within this time120msIf it drifts significantly
P9595% complete within; the power-user experience350msP95 > SLO threshold
P99Worst-case for 99% of users; tail latency1200msP99 > 3× P95 = hot spots
P99.9The "long tail" — rare but impactful at scale5000msHigh-volume or financial APIs
💡 Google SRE Rule: Define SLOs based on P99, not averages. At 1M requests/day, P99 means 10,000 users see bad performance. That's not edge-case — that's your most engaged users. 
# Prometheus: measure response time histograms
from prometheus_client import Histogram, start_http_server
import time, functools

REQUEST_TIME = Histogram(
    'request_duration_seconds',
    'HTTP request latency',
    ['method', 'endpoint', 'status'],
    buckets=[.005, .01, .025, .05, .1, .25, .5, 1, 2.5, 5]
)

def track_latency(func):
    @functools.wraps(func)
    async def wrapper(*args, **kwargs):
        start = time.time()
        status = "200"
        try:
            result = await func(*args, **kwargs)
            return result
        except Exception as e:
            status = "500"
            raise
        finally:
            REQUEST_TIME.labels(
                method="GET", endpoint=func.__name__, status=status
            ).observe(time.time() - start)
    return wrapper

CPU & Memory Profiling

When latency is high, profiling tells you exactly which function is the bottleneck. Never guess — always profile.

CPU Profiling

Identifies which functions consume the most CPU time. Hot paths = candidates for optimization.

  • Python: cProfile, py-spy (low overhead, production-safe)
  • Node.js: --prof flag, 0x flame graphs
  • Go: pprof built-in, go tool pprof
  • JVM: async-profiler, JFR, YourKit
Memory Profiling

Finds memory leaks, excessive allocations, GC pressure. Critical for long-running services.

  • Python: memory_profiler, tracemalloc, objgraph
  • Node.js: --heap-snapshot, clinic.js
  • Go: pprof heap profile, runtime.MemStats
  • JVM: Eclipse MAT, heap dumps + jmap
# Go: built-in pprof profiling endpoint
import (
    "net/http"
    _ "net/http/pprof"  // registers /debug/pprof endpoints
    "runtime"
)

func main() {
    // Enable mutex and block profiling
    runtime.SetMutexProfileFraction(1)
    runtime.SetBlockProfileRate(1)

    // Start pprof server on separate port
    go http.ListenAndServe(":6060", nil)

    // Your main app...
}

// JVM: G1GC tuning for low-latency APIs (recommended for most services)
java -server \
  -Xms4g -Xmx4g \                    // Set min = max to avoid heap resize pauses
  -XX:+UseG1GC \                      // G1GC: good balance for most workloads
  -XX:MaxGCPauseMillis=100 \          // Target pause goal (not a hard limit)
  -XX:G1HeapRegionSize=16m \          // Larger regions for large objects
  -XX:+ParallelRefProcEnabled \       // Parallel reference processing
  -XX:+DisableExplicitGC \            // Prevent System.gc() calls
  -XX:+PrintGCDetails \               // Log GC events for analysis
  -Xlog:gc*:file=/var/log/gc.log \
  -jar app.jar

// For ultra-low latency (<10ms pauses): use ZGC (Java 15+)
// -XX:+UseZGC  → sub-millisecond pauses, scales to TB heaps

Load Testing

You cannot know how your system behaves under load until you test it. Load testing before production — not after.

1
Baseline Test — establish current performance: P50/P95/P99 at normal load (e.g., 100 RPS)
2
Load Test — ramp up to expected peak load (e.g., 1000 RPS). Find where errors start
3
Stress Test — push to breaking point. Find the system's maximum capacity before failure
4
Soak Test — run at 70% capacity for 24+ hours. Catch memory leaks and connection pool exhaustion
5
Spike Test — sudden 10× load increase. Tests autoscaling and connection pooling behavior
# k6: modern, developer-friendly load testing (JavaScript)
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Rate, Trend } from 'k6/metrics';

const errorRate = new Rate('errors');
const apiLatency = new Trend('api_latency');

export const options = {
  stages: [
    { duration: '2m', target: 100 },   // ramp up
    { duration: '5m', target: 1000 },  // peak load
    { duration: '2m', target: 0 },     // ramp down
  ],
  thresholds: {
    'http_req_duration': ['p(95)<500'],  // P95 must be <500ms
    'http_req_failed': ['rate<0.01'],    // Error rate <1%
    'errors': ['rate<0.05'],
  },
};

export default function() {
  const start = Date.now();
  const res = http.get('https://api.example.com/users', {
    headers: { Authorization: 'Bearer token123' }
  });
  apiLatency.add(Date.now() - start);
  errorRate.add(res.status !== 200);

  check(res, {
    'status is 200': r => r.status === 200,
    'response <500ms': r => r.timings.duration < 500,
  });
  sleep(1);
}

Performance Optimization Patterns

❌ Common Bottlenecks
  • Synchronous external calls — blocking the event loop waiting for HTTP/DB
  • N+1 queries — loading related entities one by one in a loop
  • No connection pooling — opening a new DB connection per request
  • Serializing large objects — JSON.stringify on 10MB objects per request
  • Missing indexes — full table scans on frequently queried columns
  • Unbounded queries — SELECT * without LIMIT on large tables
✅ Optimization Techniques
  • Parallelize I/O — Promise.all / goroutines / asyncio.gather for concurrent calls
  • Batch queries — DataLoader, batch inserts, bulk operations
  • Connection pooling — PgBouncer, HikariCP, sqlalchemy pool
  • Response compression — gzip/brotli reduces payload 60-90%
  • Pagination — cursor-based pagination for large result sets
  • Read replicas — offload reads to replica, writes to primary
// Node.js: parallelize independent async operations

// ❌ BAD: sequential — total time = t1 + t2 + t3
const user = await getUser(userId);
const orders = await getOrders(userId);
const preferences = await getPreferences(userId);

// ✅ GOOD: parallel — total time = max(t1, t2, t3)
const [user, orders, preferences] = await Promise.all([
  getUser(userId),
  getOrders(userId),
  getPreferences(userId),
]);

// ✅ BETTER: also handle partial failures gracefully
const results = await Promise.allSettled([
  getUser(userId),
  getOrders(userId),
  getPreferences(userId),
]);
const [userResult, ordersResult, prefsResult] = results;
const user = userResult.status === 'fulfilled' ? userResult.value : null;

Connection Pool Sizing

The "right" pool size is not "as large as possible." Too many connections overwhelm the database. The formula: pool_size = (core_count * 2) + disk_spindles (HikariCP / PgBouncer guidance).

# PostgreSQL connection pool with asyncpg (Python)
import asyncpg
import asyncio

async def create_pool():
    return await asyncpg.create_pool(
        dsn="postgresql://user:pass@localhost/mydb",
        min_size=5,           # minimum connections to keep alive
        max_size=20,          # max concurrent connections
        max_inactive_connection_lifetime=300,  # recycle idle connections
        command_timeout=60,   # kill queries that take >60s
    )

pool = await create_pool()

async def get_user(user_id: int):
    async with pool.acquire() as conn:  # acquire from pool
        return await conn.fetchrow(
            "SELECT * FROM users WHERE id = $1", user_id
        )
    # connection automatically returned to pool on exit
⚠️ Pool Exhaustion: When all pool connections are in use, new requests queue or fail. Monitor pool.size, pool.checkedout, and pool.overflow. Alert when utilization exceeds 80%. Netflix found that connection pool exhaustion — not DB slowness — caused most of their database-related incidents.
