Chapter 5

Caching Masterclass

Caching is the single highest-leverage optimization in backend engineering. A well-designed cache layer can reduce database load by 90%, cut latency from 200ms to 2ms, and save millions in infrastructure costs.

⏱ 65 min read 🎯 Beginner → Staff 💾 Redis deep dive

Why Caching?

Databases are designed for durability and correctness, not speed. A PostgreSQL query might take 50ms; the same data served from Redis takes 0.1ms — 500× faster.

WHY
Why cache exists
Repeated database queries for the same data waste CPU and I/O. Cache eliminates redundant work. Twitter serves ~18B reads/day — impossible without caching
WHAT
What to cache
Read-heavy, infrequently changing data: user profiles, product listings, session data, computed aggregates, HTML fragments
WHERE
Cache layers
CDN (static assets) → Edge cache → Application cache (Redis/Memcached) → DB query cache → CPU L1/L2/L3
WHO
Who manages it
Application engineers define cache keys/TTLs; SREs manage Redis cluster; DBAs advise on what's safe to cache
WHEN
When to cache
When DB queries are slow AND data doesn't change on every write. Not suitable for real-time financial balances or auth tokens that need instant invalidation
HOW
How it works
On read: check cache → hit: return cached. miss: query DB → store in cache → return. Key = deterministic string based on query parameters

Cache Strategies

StrategyRead PathWrite PathBest ForDrawback
Cache-Aside (Lazy Loading)App checks cache, on miss loads DB + populates cacheApp writes to DB, invalidates cache keyMost general use casesFirst request always misses (cold start)
Write-ThroughAlways reads from cacheApp writes to cache AND DB synchronouslyRead-heavy with low write latency requirementCache has stale keys for unread data
Write-Behind (Write-Back)Reads from cacheWrites to cache only; async flush to DBWrite-heavy workloads, session storesData loss if cache fails before flush
Write-AroundCache miss → DB (data not cached on write)Writes directly to DB, bypasses cacheOne-time write bulk data (logs, analytics)High cache miss rate for new data
Read-ThroughCache fetches from DB on miss (cache does the work)App writes to DBWhen cache handles DB logic (e.g. Ehcache)Cache library must know how to load data
 
# Cache-Aside pattern (most common) — Python + Redis
import redis
import json
from typing import Optional

redis_client = redis.Redis(host='localhost', port=6379, decode_responses=True)

async def get_user(user_id: int) -> dict:
    cache_key = f"user:{user_id}"

    # 1. Check cache first
    cached = redis_client.get(cache_key)
    if cached:
        return json.loads(cached)  # cache HIT — 0.1ms

    # 2. Cache miss — query database
    user = await db.fetchrow("SELECT * FROM users WHERE id=$1", user_id)
    if not user:
        return None

    # 3. Populate cache with TTL
    redis_client.setex(
        cache_key,
        3600,                    # TTL: 1 hour
        json.dumps(dict(user))
    )
    return dict(user)

async def update_user(user_id: int, data: dict):
    await db.execute("UPDATE users SET ... WHERE id=$1", user_id)
    redis_client.delete(f"user:{user_id}")  # Invalidate cache on write

Redis Deep Dive

Redis is not just a cache — it's a data structure server. Understanding its data types unlocks powerful patterns.

Redis Data Structures
  • String: cache values, counters, distributed locks
  • Hash: user profiles, object fields (memory-efficient)
  • List: queues, activity feeds, recent items
  • Set: unique visitors, tags, relationships
  • Sorted Set: leaderboards, rate limiting, time-series
  • HyperLogLog: approximate unique counts (12KB for any cardinality)
  • Stream: event log, message queue (Kafka-lite)
  • Bitmap: feature flags, daily active user tracking

# Redis: Leaderboard with Sorted Set (used by games, Twitter trending)
import redis
r = redis.Redis()

# Add/update scores
r.zadd('leaderboard:weekly', {'user:1001': 9850, 'user:1002': 12300})
r.zincrby('leaderboard:weekly', 500, 'user:1001')  # += 500 points

# Get top 10 with scores
top10 = r.zrevrange('leaderboard:weekly', 0, 9, withscores=True)

# Get user's rank (0-indexed)
rank = r.zrevrank('leaderboard:weekly', 'user:1001')

# Redis: Distributed Lock (for preventing race conditions)
import uuid
lock_key = "lock:payment:order:123"
lock_id = str(uuid.uuid4())

# SET key value NX PX (only set if not exists, with expiry)
acquired = r.set(lock_key, lock_id, nx=True, px=30000)  # 30s TTL
if acquired:
    try:
        # Do critical section work
        process_payment()
    finally:
        # Only release if we still own the lock (Lua for atomicity)
        lua_script = """
        if redis.call("get", KEYS[1]) == ARGV[1] then
            return redis.call("del", KEYS[1])
        else return 0 end
        """
        r.eval(lua_script, 1, lock_key, lock_id)

Cache Invalidation — The Hardest Problem

"There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton
Invalidation Strategies
  • TTL-based: let keys expire automatically. Simple but can serve stale data
  • Event-based: delete/update cache on every write. Consistent but adds write complexity
  • Write-through: update cache on write. Always fresh but more writes
  • Versioned keys: user:1001:v3 — new version on every update, old keys expire naturally
  • CDC (Change Data Capture): Debezium watches DB binlog → publishes events → cache layer listens and invalidates. Used by Airbnb
Cache Key Design

Good cache keys are deterministic, readable, and namespace-isolated.

# Pattern: service:entity:id:version
"users:profile:1001"
"products:detail:SKU-123"
"search:results:hash(query)"
"session:user:1001:token"

# For complex queries, hash the params:
import hashlib, json
def cache_key(prefix, params):
    h = hashlib.md5(
        json.dumps(params, sort_keys=True).encode()
    ).hexdigest()[:8]
    return f"{prefix}:{h}"

Cache Failure Modes

Three failure modes that can take down your entire backend. Know them deeply — they appear in every system design interview.

1
Cache Stampede (Thundering Herd) — A popular key expires. Thousands of requests simultaneously find a miss and all hammer the DB at once. Fix: Use probabilistic early expiration (XFetch), mutex locks on cache miss, or background refresh. 
# Fix: mutex lock on cache miss
lock = redis.set(f"lock:{key}", 1, nx=True, ex=10)
if lock:  # we got the lock — fetch from DB
    value = fetch_from_db(key)
    redis.setex(key, 3600, value)
    redis.delete(f"lock:{key}")
else:  # wait and retry
    time.sleep(0.05)
    value = redis.get(key)  # should be populated now
2
Cache Avalanche — Many cache keys expire at the same time (e.g., all set with the same TTL at startup). Mass DB overload. Fix: Add random jitter to TTLs so expiry is spread out. 
import random
base_ttl = 3600
jitter = random.randint(0, 300)  # ±0-5 minute variation
redis.setex(key, base_ttl + jitter, value)
3
Cache Penetration — Requests for keys that don't exist in cache OR database (e.g., GET /user/999999). Cache never helps; DB is hammered. Fix: Cache null results with a short TTL, or use a Bloom Filter to reject clearly invalid keys. 
# Cache null results to prevent penetration
user = fetch_from_db(user_id)
if user is None:
    redis.setex(f"user:{user_id}", 60, "NULL")  # short TTL for nulls
else:
    redis.setex(f"user:{user_id}", 3600, json.dumps(user))
