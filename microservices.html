Chapter 9

Microservices Architecture

Microservices enable Netflix to deploy 100+ times a day. But they also introduce distributed system complexity. Master service decomposition, API gateways, service mesh, and the real cost of microservices.

⏱ 70 min read 🎯 Senior → Staff 🧩 Decomposition strategies

Monolith vs Microservices

⚠️ Start with a monolith. Martin Fowler's Microservices Premium: microservices add operational complexity. You need container orchestration, distributed tracing, service discovery, and more. Only move to microservices when a monolith genuinely hurts you — usually at 50+ engineers or when deployment coupling blocks teams.
Monolith
  • ✅ Simple to develop, test, and deploy initially
  • ✅ Easy to reason about data consistency (one DB)
  • ✅ Low latency (in-process calls, no network)
  • ✅ Easier debugging (one log stream)
  • ❌ Single team bottleneck as org grows
  • ❌ Deploy entire app for any change
  • ❌ Can't scale individual components
  • ❌ Tech stack locked for entire app

Shopify Basecamp — successful large-scale monoliths

Microservices
  • ✅ Independent deployments (team autonomy)
  • ✅ Scale individual services independently
  • ✅ Technology diversity (right tool per service)
  • ✅ Fault isolation (one service fails, others continue)
  • ❌ Network calls add latency + failure modes
  • ❌ Distributed transactions are complex
  • ❌ Observability requires tooling investment
  • ❌ Significant ops overhead (k8s, service mesh)

API Gateway

The API Gateway is the entry point for all client traffic. It handles cross-cutting concerns so individual services don't have to.

API Gateway Responsibilities
  • Routing: /users → UserService, /orders → OrderService
  • Authentication: validate JWT once at gateway, not per-service
  • Rate limiting: protect backends from abuse
  • SSL termination: decrypt TLS once at gateway
  • Request aggregation: combine multiple service calls
  • Protocol translation: REST to gRPC internally
  • Load balancing: distribute across service instances
Popular API Gateways
  • Kong: open-source, plugin-based, high performance
  • AWS API Gateway: serverless, native Lambda integration
  • Nginx / Traefik: lightweight reverse proxy + gateway
  • Istio Ingress: service mesh gateway with full observability
  • GraphQL Gateway: Apollo Federation for schema stitching

Netflix uses Zuul/Spring Cloud Gateway. Airbnb uses SmartStack. Lyft built Envoy (now used everywhere).

Service Mesh

A service mesh handles service-to-service communication: mutual TLS, retries, circuit breaking, observability — all without application code changes.

1
Sidecar Proxy — Each service pod gets an Envoy/Linkerd proxy sidecar. All traffic flows through the sidecar, not directly between services
2
Control Plane — Istio's control plane pushes config to all sidecars: routing rules, TLS certificates, retry policies, circuit breaker settings
3
mTLS — Mutual TLS between all services, automatically. No certificate management in application code
4
Observability — Every request automatically traced. Latency, error rates, and traffic flows visible in Grafana/Jaeger without instrumentation

Designing Good Microservices

💡 The Rule of Two Pizzas: A microservice should be small enough for two pizzas to feed the team that owns it. But don't make services TOO small — nanoservices add network overhead and operational complexity without benefit.
✅ Good Microservice Design
  • Single responsibility — one bounded context
  • Own its own data (no shared databases)
  • Communicate via APIs or events, not direct DB access
  • Can be deployed independently without coordinating with other teams
  • Stateless: state in DB/Redis, not in-memory
  • Graceful degradation: works (degraded) if dependencies fail
❌ Anti-patterns
  • Shared database — tight coupling, defeats the purpose
  • Synchronous chains — ServiceA → B → C → D: single failure cascades
  • Chatty services — 50 calls to render one page: latency disaster
  • Versioning neglect — breaking API changes affect all consumers
  • No circuit breakers — one slow service hangs all callers
  • Distributed monolith — services that must be deployed together
# Service-to-service communication with retry + circuit breaker
# Using tenacity (Python) + httpx
import httpx
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=1, max=10),  # 1s, 2s, 4s backoff
    retry=retry_if_exception_type((httpx.TransportError, httpx.TimeoutException)),
)
async def get_user_profile(user_id: str) -> dict:
    async with httpx.AsyncClient(timeout=2.0) as client:
        response = await client.get(
            f"http://user-service/users/{user_id}",
            headers={"X-Request-ID": get_trace_id()}  # propagate trace
        )
        response.raise_for_status()
        return response.json()

# Fallback on circuit open
async def get_user_profile_safe(user_id: str) -> dict:
    try:
        return await get_user_profile(user_id)
    except Exception:
        return {"id": user_id, "name": "Unknown", "degraded": True}
