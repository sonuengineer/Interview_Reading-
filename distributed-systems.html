Chapter 8

Distributed Systems Masterclass

The hardest problems in software engineering are distributed problems. CAP theorem, consensus, eventual consistency, SAGA patterns — understand the tradeoffs that define every large-scale system.

⏱ 80 min read 🎯 Senior → Principal 🌐 CAP, SAGA, CQRS

CAP Theorem

In a distributed system, you can only guarantee 2 of 3 properties simultaneously. This is not a choice you make at design time — it's a physical constraint of networks.

C — Consistency

Every read returns the most recent write (or an error). All nodes see the same data at the same time.

Example: After writing balance=500, any subsequent read on any node returns 500, not an old value.

A — Availability

Every request receives a response (not necessarily the latest data). System never refuses.

Example: Even if some nodes are down, the system responds — possibly with stale data.

P — Partition Tolerance

System continues operating even when network partitions occur (some nodes can't communicate).

In practice, P is always required — networks do partition. So the real choice is C vs A during partitions.

SystemTypeTradeoffExample DBs
CPConsistent + Partition TolerantMay become unavailable during partitions. Refuses stale readsHBase, Zookeeper, etcd, MongoDB (strong), Redis (cluster)
APAvailable + Partition TolerantReturns potentially stale data. Never refuses requestsCassandra, DynamoDB (eventual), CouchDB
CAConsistent + AvailableCannot tolerate network partitions — not practical at scaleSingle-node RDBMS (PostgreSQL on one machine)
💡 PACELC: CAP only describes behavior during partitions. PACELC extends this: even when the system is running normally (no partition), there's a tradeoff between Latency and Consistency. DynamoDB chose A over C during partitions, and L over C during normal operation — that's how it achieves single-digit ms latency.

Consistency Models

ModelGuaranteePerformanceUsed By
LinearizabilityStrongest. Operations appear instantaneous and globally orderedSlowest (consensus required)Spanner, etcd, Zookeeper
SequentialAll operations appear in the same order to all nodes, but may lagModerateMulti-primary replication
CausalCausally related operations are ordered. Unrelated may be concurrentGoodMongoDB sessions, CockroachDB
EventualAll replicas converge to same value eventually. No ordering guaranteesFastestDynamoDB, Cassandra, DNS

Consensus & Leader Election

Consensus algorithms allow distributed nodes to agree on a single value even when nodes fail. This is how distributed DBs elect a primary and Kubernetes elects a controller.

Raft Consensus

The most understandable consensus algorithm. Used by etcd, CockroachDB, TiKV.

  • One Leader, multiple Followers
  • Leader handles all writes; replicates to followers
  • If leader fails, followers hold election
  • Candidate with most up-to-date log wins
  • Requires quorum (n/2 + 1 nodes) to commit
Paxos (Brief)

The original consensus algorithm. Notoriously hard to understand and implement. Used by Google Chubby, Spanner.

  • Two phases: Prepare and Accept
  • More flexible than Raft but much harder to reason about
  • Multi-Paxos adds leader optimization
  • Most real-world systems use Raft or Paxos variants

SAGA Pattern

Distributed transactions are hard — 2PC (two-phase commit) blocks resources and fails in high-latency environments. SAGA is the modern alternative: a sequence of local transactions, each publishing events that trigger the next step.

1
Order Service: Create order (status=PENDING) → publish OrderCreated event
2
Payment Service: Process payment → publish PaymentProcessed or PaymentFailed
3
Inventory Service: Reserve stock → publish StockReserved or StockInsufficient
4
Shipping Service: Create shipment → publish ShipmentCreated
5
On any failure: Run compensating transactions backwards — refund payment, release stock, cancel order
Choreography SAGA

Services communicate via events. No central coordinator. Each service knows what events to react to.

  • ✅ Loose coupling, no single point of failure
  • ✅ Each service is fully autonomous
  • ❌ Hard to track global state (where did the saga fail?)
  • ❌ Complex to debug across multiple event streams
Orchestration SAGA

A central Saga Orchestrator coordinates all steps and handles compensations. Used by Netflix Conductor, Temporal.

  • ✅ Clear visibility into saga state and progress
  • ✅ Easy to add/modify steps centrally
  • ❌ Orchestrator becomes a coupling point
  • ❌ Single component to maintain and scale

Resilience Patterns

// Circuit Breaker pattern (TypeScript)
enum State { CLOSED, OPEN, HALF_OPEN }

class CircuitBreaker {
  private state = State.CLOSED;
  private failureCount = 0;
  private lastFailureTime = 0;
  private readonly threshold = 5;   // open after 5 failures
  private readonly timeout = 60000;  // retry after 60s

  async call<T>(fn: () => Promise<T>): Promise<T> {
    if (this.state === State.OPEN) {
      if (Date.now() - this.lastFailureTime > this.timeout) {
        this.state = State.HALF_OPEN;  // try one request
      } else {
        throw new Error('Circuit breaker OPEN — fast fail');
      }
    }
    try {
      const result = await fn();
      this.onSuccess();
      return result;
    } catch (err) {
      this.onFailure();
      throw err;
    }
  }
  private onSuccess() {
    this.failureCount = 0;
    this.state = State.CLOSED;
  }
  private onFailure() {
    this.failureCount++;
    this.lastFailureTime = Date.now();
    if (this.failureCount >= this.threshold) this.state = State.OPEN;
  }
}

CQRS & Event Sourcing

CQRS

Command Query Responsibility Segregation — separate read and write models. Writes go to a normalized write DB; reads use a denormalized read DB optimized for queries.

Used by: Airbnb (search separate from booking), LinkedIn (feed separate from social graph)

Event Sourcing

Instead of storing current state, store a log of events. Current state is derived by replaying events. Complete audit trail, time travel, and easy event replay.

Used by: Banks (transaction ledger), Git (commits as events), Kafka-based systems
