Chapter 7

Message Queues & Event Streaming

Queues decouple producers from consumers, enabling async processing, load leveling, and fault tolerance. From SQS to Kafka — master the full spectrum of async messaging patterns.

⏱ 65 min read 🎯 Intermediate → Staff 📬 Kafka deep dive

Why Message Queues?

WHY
Why queues exist
Synchronous calls fail if the downstream service is down. Queues absorb spikes, retry failures, and decouple services so they can fail independently
WHAT
What they do
Buffer messages between services. Producer writes to queue; consumer reads at its own pace. Messages persist if consumer is down
WHERE
Use cases
Email/notification sending, order processing, video transcoding, fraud detection, event pipelines, log aggregation, microservice communication
WHO
Who uses it
Netflix uses Kafka for 2+ trillion events/day. Uber uses Kafka for trip events. LinkedIn invented Kafka. Stripe uses SQS for payment events
WHEN
When to use
Response time doesn't need to be immediate; work can be retried; downstream services have different scaling needs; fire-and-forget is acceptable
HOW
How it works
Producer sends message to queue/topic → Broker persists it → Consumer polls or is pushed → Consumer processes → Acknowledges → Broker removes

Apache Kafka Deep Dive

Kafka is a distributed, fault-tolerant, high-throughput event streaming platform. It's not a traditional queue — it's a log. Messages are retained and can be replayed.

ConceptDescriptionAnalogy
TopicA named category of messages (like a table in a DB)A TV channel
PartitionA topic is split into N partitions for parallelism. Each partition is an ordered logMultiple lanes on a highway
OffsetSequential ID for each message within a partition. Consumers track their offsetPage number in a book
Consumer GroupA group of consumers that divide partition work between them. Each partition goes to exactly one consumer in the groupA team dividing chapters to read
BrokerA Kafka server node. Cluster = multiple brokers for fault tolerancePost office branch
ProducerWrites messages to topics. Can choose partition via key hashingLetter writer
Replication FactorEach partition is replicated across N brokers. RF=3 means 2 broker failures toleratedMaking 3 copies of a document
 
# Kafka producer (Python confluent-kafka)
from confluent_kafka import Producer
import json

producer = Producer({'bootstrap.servers': 'kafka:9092'})

def publish_order_event(order_id: str, event_type: str, data: dict):
    message = {
        "eventType": event_type,  # "ORDER_PLACED", "ORDER_SHIPPED"
        "orderId": order_id,
        "timestamp": datetime.utcnow().isoformat(),
        "data": data
    }
    producer.produce(
        topic='orders',
        key=order_id.encode(),       # same order → same partition (ordering)
        value=json.dumps(message).encode(),
        callback=lambda err, msg: print(f"Delivered: {msg.offset()}") if not err else print(err)
    )
    producer.flush()

# Kafka consumer (Python)
from confluent_kafka import Consumer

consumer = Consumer({
    'bootstrap.servers': 'kafka:9092',
    'group.id': 'order-processing-service',  # consumer group
    'auto.offset.reset': 'earliest',           # start from beginning if new group
    'enable.auto.commit': False,                # manual commit for exactly-once
})
consumer.subscribe(['orders'])

while True:
    msg = consumer.poll(timeout=1.0)
    if msg is None: continue
    if msg.error(): handle_error(msg.error()); continue

    event = json.loads(msg.value())
    try:
        process_order_event(event)
        consumer.commit(message=msg)  # only commit on success
    except Exception as e:
        send_to_dlq(event, str(e))    # dead letter queue on failure
        consumer.commit(message=msg)  # commit to move on

Delivery Semantics

SemanticMeaningRiskUse Case
At Most OnceMessage delivered 0 or 1 times. Fire-and-forget, no retryMessage loss on failureMetrics, logging, non-critical notifications
At Least OnceMessage delivered 1+ times. Retry on failure. May duplicateDuplicate processingMost use cases with idempotent consumers
Exactly OnceMessage delivered exactly 1 time. No loss, no duplicatesComplex, lower throughputFinancial transactions, inventory updates
💡 At Least Once + Idempotent Consumers is the industry standard. Design your consumer to be idempotent — processing the same message twice has no additional effect. Store message_id in a processed-set (Redis or DB). Check before processing. This is simpler and more reliable than true exactly-once.

Messaging Patterns

Queue (Point-to-Point)

One producer, one consumer. Message removed after consumption. Used in SQS, RabbitMQ.

  • Load leveling: buffer bursts of work
  • Task distribution: divide work across workers
  • Retry with backoff + DLQ for poison messages
  • Example: order processing, email sending
Pub/Sub (Fan-Out)

One producer, many consumers. All subscribers get the message. Used in Kafka, SNS, Redis Pub/Sub.

  • Event broadcasting: "order placed" → inventory, email, analytics all receive it
  • Event sourcing: all services react to the same event
  • Example: Stripe webhook → your listeners

Dead Letter Queues

A DLQ captures messages that failed processing after N retries. Without a DLQ, a poison message can block the entire queue forever (head-of-line blocking).

# AWS SQS with Dead Letter Queue (Python boto3)
import boto3, json
sqs = boto3.client('sqs', region_name='us-east-1')

# Create main queue with DLQ configured
dlq_url = sqs.create_queue(QueueName='orders-dlq')['QueueUrl']
dlq_arn = sqs.get_queue_attributes(QueueUrl=dlq_url, AttributeNames=['QueueArn'])['Attributes']['QueueArn']

main_queue = sqs.create_queue(
    QueueName='orders',
    Attributes={
        'RedrivePolicy': json.dumps({
            'deadLetterTargetArn': dlq_arn,
            'maxReceiveCount': '3'  # after 3 failures → send to DLQ
        }),
        'VisibilityTimeout': '30'  # 30s processing window
    }
)

# Consumer with error handling
def process_messages():
    while True:
        response = sqs.receive_message(
            QueueUrl=main_queue['QueueUrl'],
            MaxNumberOfMessages=10,
            WaitTimeSeconds=20  # long polling — reduces empty receives
        )
        for msg in response.get('Messages', []):
            try:
                process_order(json.loads(msg['Body']))
                sqs.delete_message(  # ACK: remove from queue
                    QueueUrl=main_queue['QueueUrl'],
                    ReceiptHandle=msg['ReceiptHandle']
                )
            except Exception:
                pass  # visibility timeout expires → SQS retries → after 3x → DLQ
