CI/CD & DevOps

From commit to production in minutes, not weeks. Master Docker containers, Kubernetes orchestration, GitHub Actions pipelines, and the DevOps practices that let teams at Google and Netflix deploy hundreds of times per day.

⏱ 90 min read 🎯 Mid-level → Senior 🔧 Docker, K8s, GitHub Actions 🚀 Deploy 100×/day

Why DevOps? The DORA Metrics

DevOps Research and Assessment (DORA) tracks 4 metrics that predict software delivery performance. Elite teams score dramatically better on all four — and those teams have 2× lower change failure rates and 24× faster recovery times.

~1h
Elite lead time (commit → prod)
~180×
Elite deploy frequency
<1h
Elite mean time to restore
<5%
Elite change failure rate
💡
Shift Left

"Shift left" means moving quality checks earlier in the pipeline — running linting, tests, and security scans at commit time rather than at deployment time. A bug caught in CI costs 10× less to fix than one caught in staging, and 100× less than one in production.

Docker — Containers Fundamentals

Why Containers?

Before containers: "it works on my machine" was a real problem. Different OS libraries, Python versions, environment variables — every environment was a snowflake. Containers package your app with all its dependencies into an isolated, reproducible unit that runs identically everywhere.

Containers vs VMs

  • Share the host OS kernel (no hypervisor)
  • Start in milliseconds (VMs: minutes)
  • ~50MB overhead vs ~1GB for VM
  • Thousands per host vs dozens for VMs
  • Trade-off: weaker isolation than VMs

When to Use VMs Instead

  • Multi-tenant security isolation required
  • Running a different kernel (Windows on Linux host)
  • Compliance requires hardware-level isolation
  • Long-running processes that don't need fast startup

Dockerfile Best Practices

Dockerfile (Node.js — production-ready)
# Stage 1: Build
FROM node:20-alpine AS builder
WORKDIR /app
# Copy package files first — leverage layer caching
# These layers only rebuild when package.json changes
COPY package*.json ./
RUN npm ci --only=production

COPY . .
RUN npm run build

# Stage 2: Runtime — final image is much smaller
FROM node:20-alpine
WORKDIR /app

# Run as non-root user (security best practice)
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

# Copy only what we need from builder
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules

EXPOSE 3000

# Use exec form (not shell form) to handle signals correctly
CMD ["node", "dist/server.js"]

Layer Caching — The Most Important Docker Optimization

Docker builds images layer by layer. Each instruction creates a layer. If a layer hasn't changed, Docker reuses the cached version. The golden rule: put things that change rarely at the top, things that change often at the bottom.

🐢
Common Mistake: COPY . . Before npm install

If you COPY . . first, then RUN npm install, the npm install layer invalidates every time ANY source file changes — even a comment. Always copy package files first, install, then copy source. This saves minutes on every build.

Docker Compose for Local Development

docker-compose.yml
version: '3.9'
services:
  api:
    build:
      context: .
      target: builder  # Use builder stage for hot-reload
    ports:
      - "3000:3000"
    volumes:
      - ./src:/app/src  # Mount source for hot-reload
    environment:
      - NODE_ENV=development
      - DATABASE_URL=postgres://user:pass@postgres:5432/mydb
    depends_on:
      postgres:
        condition: service_healthy  # Wait for DB ready

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: mydb
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user"]
      interval: 5s
      retries: 5
    volumes:
      - postgres_data:/var/lib/postgresql/data

  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]

Kubernetes — Container Orchestration

Why Kubernetes?

Docker Compose works for local dev. In production you need: automatic restarts when containers crash, rolling deploys with zero downtime, auto-scaling based on CPU/memory, service discovery between services, secrets management. Kubernetes handles all of this.

Core Concepts

ConceptWhat it isAnalogy
PodSmallest deployable unit. 1+ containers sharing network/storage.A single process (or tightly coupled group)
DeploymentManages a set of identical pods. Handles rolling updates, rollbacks.A recipe for running N copies of your app
ServiceStable DNS name + load balancer in front of pods. Pods come and go; Service stays.A load balancer that auto-updates its backend list
ConfigMapNon-sensitive config (env vars, config files) injected into pods.A .env file mounted into containers
SecretSensitive data (passwords, tokens) base64-encoded. Use external secret stores in prod.A vault-managed .env file
IngressHTTP routing rules. Routes external traffic to Services based on host/path.Nginx reverse proxy config
HPAHorizontal Pod Autoscaler. Scales replicas based on CPU/memory or custom metrics.Auto-scaling group in AWS

Production Deployment

deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
  labels:
    app: api-server
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-server
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # Allow 1 extra pod during deploy
      maxUnavailable: 0  # Never drop below 3 pods (zero-downtime)
  template:
    metadata:
      labels:
        app: api-server
    spec:
      containers:
        - name: api
          image: myregistry/api-server:1.4.2  # Always use specific tags, not :latest
          ports:
            - containerPort: 3000
          resources:
            requests:          # Guaranteed resources (affects scheduling)
              cpu: "100m"
              memory: "128Mi"
            limits:            # Hard cap — OOMKilled if exceeded
              cpu: "500m"
              memory: "512Mi"
          readinessProbe:    # Traffic only sent when pod is ready
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:     # Pod restarted if this fails
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 15
            periodSeconds: 30
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: api-secrets
                  key: database-url

Horizontal Pod Autoscaler

hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-server
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70  # Scale out at 70% CPU
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
⚠
Never Use :latest in Production

Using image: myapp:latest means rolling back is impossible — you don't know what "latest" was before the deploy. Always tag images with the Git commit SHA (myapp:abc1234) or semantic version (myapp:1.4.2). This makes every deploy reproducible and rollbacks instant.

Complete GitHub Actions Workflow

.github/workflows/deploy.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # ── Stage 1: Quality Gates ─────────────────────
  lint-and-test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: testpass
          POSTGRES_DB: testdb
        options: >-
          --health-cmd pg_isready
          --health-interval 10s

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'  # Cache node_modules between runs

      - run: npm ci

      - name: Lint
        run: npm run lint

      - name: Type check
        run: npm run typecheck

      - name: Unit tests
        run: npm test -- --coverage

      - name: Integration tests
        run: npm run test:integration
        env:
          DATABASE_URL: postgres://postgres:testpass@localhost:5432/testdb

      - name: Upload coverage
        uses: codecov/codecov-action@v4

  # ── Stage 2: Build & Push Image ────────────────
  build-and-push:
    needs: lint-and-test
    runs-on: ubuntu-latest
    if: github.event_name == 'push'
    permissions:
      contents: read
      packages: write

    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}
      image-digest: ${{ steps.build.outputs.digest }}

    steps:
      - uses: actions/checkout@v4

      - name: Log in to registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha,prefix=  # Tag with git SHA
            type=ref,event=branch

      - name: Build and push
        id: build
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha    # Use GitHub Actions cache
          cache-to: type=gha,mode=max

  # ── Stage 3: Deploy to Staging ─────────────────
  deploy-staging:
    needs: build-and-push
    runs-on: ubuntu-latest
    environment: staging

    steps:
      - name: Deploy to Kubernetes
        uses: azure/k8s-deploy@v4
        with:
          namespace: staging
          manifests: k8s/staging/
          images: ${{ needs.build-and-push.outputs.image-tag }}

      - name: Smoke tests
        run: npm run test:smoke -- --env=staging

Infrastructure as Code — Terraform

Why IaC?

Manually clicking through AWS console leads to drift: your prod environment slowly becomes different from staging, no one knows what's deployed, and recreating it is impossible. Infrastructure as Code means your infrastructure is in git — versioned, reviewed, reproducible.

main.tf — EKS Cluster (simplified)
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
  # Store state in S3, lock in DynamoDB
  backend "s3" {
    bucket         = "mycompany-terraform-state"
    key            = "prod/eks/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-state-lock"
    encrypt        = true
  }
}

module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 20.0"

  cluster_name    = "prod-cluster"
  cluster_version = "1.30"
  vpc_id          = module.vpc.vpc_id
  subnet_ids      = module.vpc.private_subnets

  eks_managed_node_groups = {
    general = {
      desired_size = 3
      min_size     = 2
      max_size     = 10
      instance_types = ["t3.medium"]
    }
  }
}

Terraform Workflow

1

terraform init

Downloads providers and modules. Initializes the backend (S3). Run once per workspace setup.

2

terraform plan

Shows what will change: + create, ~ modify, - destroy. Always review this output before applying. Post the plan as a PR comment in CI.

3

terraform apply

Makes the actual changes. In production, only run this from CI/CD after PR approval, never from a developer's laptop. Prevents "it worked fine on my machine" infrastructure drift.

4

terraform state

Terraform tracks current state in a state file. Store it in S3 with DynamoDB locking so multiple engineers don't corrupt it with concurrent applies.

GitOps — Kubernetes Deployments via Git

GitOps is a pattern where Git is the single source of truth for both application code and infrastructure state. A GitOps operator (ArgoCD, Flux) watches your Git repo and automatically syncs the cluster to match whatever is in the repo.

  Developer
     │
     │ git push (app code)
     ▼
  GitHub (app repo)           GitHub (config repo)
     │                              ▲
     │ CI builds image              │ CI updates image tag
     ▼                              │ (e.g. deployment.yaml)
  Container Registry ──────────────┘
                                    │
                               ArgoCD watches config repo
                                    │
                                    ▼
                           Kubernetes Cluster
                           (auto-synced to match git)

ArgoCD Application

argocd-app.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-server
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/mycompany/k8s-manifests
    targetRevision: HEAD
    path: apps/api-server/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true     # Remove resources deleted from git
      selfHeal: true  # Revert manual kubectl changes

Secrets Management

Never store secrets in git. Even in a private repo — anyone with read access can steal credentials, and rotating them after a leak is painful. Use a proper secrets manager and inject at runtime.

ToolBest ForKey Feature
HashiCorp VaultSelf-hosted, fine-grained access controlDynamic secrets — generates DB creds per-request, auto-rotates
AWS Secrets ManagerAWS-native workloadsAutomatic rotation for RDS, auto-inject to ECS/EKS
GitHub Actions SecretsCI/CD pipeline secretsEncrypted at rest, masked in logs, org-level sharing
External Secrets OperatorKubernetes + any backendSyncs Vault/AWS/GCP secrets into K8s Secrets automatically
🚨
Common Secret Leaks

Secrets leak through: git history (even after deletion — always rotate!), Docker image ENV layers (visible in docker inspect), log files, error messages, environment dumps. Use --build-arg secrets in Dockerfiles (never ENV DB_PASS=...). Add git-secrets or truffleHog to your pre-commit hooks.

DevOps Production Checklist

  • Multi-stage builds — runtime image contains no build tools
  • Non-root user in container
  • No secrets in ENV instructions or image layers
  • Specific base image tag pinned (not :latest)
  • .dockerignore excludes node_modules, .git, .env
  • Package files copied before source (layer cache optimization)
  • HEALTHCHECK instruction defined
  • CMD uses exec form (JSON array) for signal handling
  • Resource requests and limits set on all containers
  • Readiness and liveness probes configured
  • Image tag is specific (git SHA), never :latest
  • Secrets stored in Kubernetes Secrets, not ConfigMaps
  • HPA configured for auto-scaling
  • PodDisruptionBudget set (prevents full outage during node drain)
  • Network policies restrict inter-pod communication
  • Namespace resource quotas prevent runaway usage
  • CI runs on every PR — no merge without passing CI
  • Tests run in parallel where possible
  • Build artifacts (images) tagged with commit SHA
  • Deploy to staging before production
  • Smoke tests run post-deploy
  • Automatic rollback on smoke test failure
  • No manual steps required for production deploy
  • Deployment pipeline history is auditable
  • Container images scanned for CVEs (Trivy, Snyk)
  • Secrets never in git, even in private repos
  • git-secrets or similar pre-commit hook installed
  • Least-privilege IAM roles for CI/CD pipeline
  • Branch protection on main — require reviews + CI
  • Signed commits / OIDC for supply chain integrity
  • Infrastructure changes require PR review (IaC)
  • Audit log for all production deployments
