Database Engineering

Databases are where data lives and where most performance problems originate. Master SQL, indexes, transactions, replication, and sharding — the skills that separate good engineers from great ones.

⏱ 90 min read🎯 All levels🗄 SQL · NoSQL · Indexing

SQL & Relational Databases

Relational databases have been the backbone of data storage since the 1970s. PostgreSQL and MySQL power the majority of production systems at companies of all sizes.

💡
Instagram's Database

Instagram served 1 billion users on PostgreSQL for years before adding sharding. Their advice: don't over-engineer early. A well-tuned PostgreSQL on good hardware can handle enormous load before you need to shard.

Essential SQL Patterns

SQL — Common Query Patterns
-- Efficient: fetch users with their order counts
SELECT
  u.id,
  u.name,
  u.email,
  COUNT(o.id) AS order_count,
  SUM(o.total) AS total_spent
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.created_at >= NOW() - INTERVAL '30 days'
GROUP BY u.id, u.name, u.email
HAVING COUNT(o.id) > 0
ORDER BY total_spent DESC
LIMIT 100;

-- Window functions: rank orders within each user
SELECT
  user_id,
  id AS order_id,
  total,
  ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rank
FROM orders;
-- rank=1 is most recent order per user

-- CTE: readable complex queries
WITH recent_orders AS (
  SELECT user_id, COUNT(*) AS cnt
  FROM orders
  WHERE created_at > NOW() - INTERVAL '7 days'
  GROUP BY user_id
),
active_users AS (
  SELECT user_id FROM recent_orders WHERE cnt >= 3
)
SELECT u.* FROM users u
JOIN active_users au ON au.user_id = u.id;

-- Upsert (INSERT or UPDATE atomically)
INSERT INTO user_stats (user_id, login_count, last_login)
VALUES (123, 1, NOW())
ON CONFLICT (user_id) DO UPDATE SET
  login_count = user_stats.login_count + 1,
  last_login = NOW();

Indexes Deep Dive

An index is a data structure that makes queries faster at the cost of storage and write speed. Understanding indexes is the single biggest lever for database performance.

Without Index (Full Table Scan):
  users table: 10,000,000 rows
  Query: SELECT * FROM users WHERE email = 'jane@example.com'
  PostgreSQL reads ALL 10M rows → ~2000ms

With B-Tree Index on email:
  Index tree → O(log n) lookups
  3 disk seeks → found! → ~1ms

  Index structure:
              [m...z]
             /       \
      [a...l]         [n...z]
     /       \       /       \
  [a-d]   [e-l]  [n-q]   [r-z]
    │                │
  alice@..        jane@.. ← found in ~3 hops
SQL — Index Strategies
-- B-Tree index (default): equality, range, sort
CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_orders_created ON orders(created_at DESC);

-- Composite index: order matters! leftmost prefix rule
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at DESC);
-- Supports: WHERE user_id = 1
-- Supports: WHERE user_id = 1 AND created_at > '2024-01-01'
-- Does NOT support: WHERE created_at > '2024-01-01' (alone)

-- Partial index: index only a subset of rows
CREATE INDEX idx_orders_pending ON orders(created_at)
  WHERE status = 'pending';
-- Much smaller index, faster for this specific query pattern

-- Covering index: index includes all columns needed
CREATE INDEX idx_users_covering ON users(email) INCLUDE (id, name);
-- Query can be satisfied entirely from index, no table lookup!

-- EXPLAIN ANALYZE: understand query execution
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 123 AND status = 'pending';

-- Bad output: Seq Scan on orders (cost=0..50000 rows=...)  ← no index used
-- Good output: Index Scan using idx_orders on orders ← index hit
-- Best output: Index Only Scan ← covering index, no heap fetch

Transactions & ACID

Transactions ensure that a group of operations either all succeed or all fail together. ACID properties define correctness guarantees.

PropertyMeaningExampleWithout It
AtomicityAll operations succeed or all failTransfer $100: debit A AND credit BMoney disappears if crash mid-transfer
ConsistencyDB moves from one valid state to anotherAccount balance can't go below -$1000Constraint violations persist
IsolationConcurrent transactions don't interfereTwo users buying last item simultaneouslyRace conditions, overselling inventory
DurabilityCommitted data survives crashesPayment confirmed = actually savedConfirmed payments lost on server restart
SQL — Transaction & Locking Patterns
-- ✅ Bank transfer with proper transaction
BEGIN;

UPDATE accounts
SET balance = balance - 100.00
WHERE id = 1 AND balance >= 100.00;  -- Check insufficient funds

IF ROW_COUNT() = 0 THEN
  ROLLBACK;
  RAISE EXCEPTION 'Insufficient funds';
END IF;

UPDATE accounts SET balance = balance + 100.00 WHERE id = 2;

INSERT INTO transactions (from_id, to_id, amount, created_at)
VALUES (1, 2, 100.00, NOW());

COMMIT;

-- Pessimistic locking: lock row for update (prevents races)
BEGIN;
SELECT quantity FROM inventory WHERE product_id = 42 FOR UPDATE;
-- Row is locked! Other transactions wait here
UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 42;
COMMIT;

-- Optimistic locking: use version column, no DB lock
SELECT id, quantity, version FROM inventory WHERE product_id = 42;
-- version = 5, quantity = 10

UPDATE inventory
SET quantity = quantity - 1, version = version + 1
WHERE product_id = 42 AND version = 5;  -- Fails if version changed
-- If 0 rows updated → conflict! Retry with fresh read

Replication

  PRIMARY (Write)              REPLICAS (Read)
  ┌─────────────────┐         ┌──────────────────┐
  │ Accepts writes  │──WAL──▶│ Replica 1 (sync) │ ← strong consistency
  │ Replication log │         └──────────────────┘
  │ (WAL stream)    │──WAL──▶┌──────────────────┐
  └─────────────────┘   async│ Replica 2        │ ← eventual consistency
                              └──────────────────┘
                         async▶┌──────────────────┐
                              │ Replica 3 (RR)   │ ← read replica
                              └──────────────────┘

  Sync replication: write confirmed only after replica acks
  → Zero data loss, but higher write latency

  Async replication: write confirmed immediately
  → Lower latency, potential data loss on primary crash
Node.js — Read/Write Splitting
const writePool = new Pool({ host: 'primary.db', max: 10 });
const readPool = new Pool({ host: 'replica.db', max: 30 });

class UserRepository {
  async findById(id) {
    // Read → replica (can handle eventual consistency)
    return readPool.query('SELECT * FROM users WHERE id = $1', [id]);
  }

  async create(data) {
    // Write → primary (must be consistent)
    return writePool.query('INSERT INTO users ... RETURNING *', data);
  }

  async findAfterCreate(id) {
    // ⚠️ Replication lag! Just created user may not be in replica yet
    // Solution 1: read from primary for this specific query
    // Solution 2: read-your-writes sticky routing to primary for 1s
    // Solution 3: wait for replication (sync replication)
    return writePool.query('SELECT * FROM users WHERE id = $1', [id]);
  }
}

Sharding

Sharding is horizontal partitioning — splitting data across multiple database servers. Use it when a single server can no longer handle your data volume or write load.

  Application
      │
      ▼
  Shard Router (consistent hashing / range-based)
  ├── user_id % 4 == 0 → Shard 0 (users 0,4,8,12...)
  ├── user_id % 4 == 1 → Shard 1 (users 1,5,9,13...)
  ├── user_id % 4 == 2 → Shard 2 (users 2,6,10,14...)
  └── user_id % 4 == 3 → Shard 3 (users 3,7,11,15...)

  Each shard is a full PostgreSQL instance
  with its own replicas, backups, etc.
⚠️
Sharding is Hard — Delay as Long as Possible

Sharding breaks cross-shard JOINs, transactions, and foreign keys. You can't do SELECT * FROM users JOIN orders if users and orders are on different shards. Uber runs thousands of PostgreSQL shards — but it took years and dedicated infrastructure teams to get there. First: optimize queries, add indexes, scale vertically, add read replicas. Shard as a last resort.

Connection Pools & N+1

SQL — N+1 Query Problem & Fix
-- ❌ N+1 Problem: 1 query to get users, then N queries for orders
-- Code: users.forEach(u => db.query('SELECT * FROM orders WHERE user_id = $1', u.id))
-- For 100 users = 101 queries!

-- ✅ Fix 1: JOIN (when you need all data together)
SELECT
  u.id, u.name,
  o.id AS order_id, o.total, o.status
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.id = ANY(ARRAY[1,2,3...100]);
-- 1 query for all users and their orders

-- ✅ Fix 2: Separate query with IN (when JOIN creates too many rows)
SELECT * FROM users WHERE id IN (1,2,3...100);  -- 1 query
SELECT * FROM orders WHERE user_id IN (1,2,3...100);  -- 1 query
-- Total: 2 queries instead of 101
