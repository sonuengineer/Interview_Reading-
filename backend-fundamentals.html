Chapter 1

Backend Fundamentals

The foundation every backend engineer must master. Understand how requests flow, how servers process them, and how the layers of a backend system work together — from the wire to the database and back.

⏱ 60 min read 🎯 Beginner → Senior 💻 Code examples included

What is Backend Engineering?

Backend engineering is the discipline of designing, building, and maintaining the server-side systems that power applications — the invisible infrastructure that handles data, business logic, authentication, and communication between systems.

WHY
Why it exists
Frontend can't store data permanently, enforce security, or handle complex business logic safely on the client side
WHAT
What it is
Server-side code, databases, APIs, caching, queues, and infrastructure that process, store, and serve data
WHERE
Where it runs
Data centers, cloud servers (AWS, GCP, Azure), containers (Docker/Kubernetes), edge networks
WHO
Who owns it
Backend engineers, platform engineers, SREs, DBAs, and cloud architects depending on the company size
WHEN
When you need it
Any time you need persistence, security, multi-user interaction, or integration with third-party services
HOW
How it works
Client sends HTTP request → server routes it → processes business logic → queries DB → returns response

The 7 Stages Explained

1

DNS Resolution

Client looks up api.example.com → DNS returns IP. Cached locally for TTL duration. First request pays DNS lookup latency (~20-100ms uncached). Companies use Anycast DNS (Cloudflare, Route 53) to route users to nearest data center. Failure mode: DNS poisoning, TTL storms during IP changes.

2

TCP Connection & TLS Handshake

TCP: 3-way handshake (SYN → SYN-ACK → ACK) adds 1 round-trip (~10-50ms on fast networks). TLS 1.3 adds ~1 RTT on top. HTTP/2 multiplexes multiple requests over one TCP connection. HTTP/3 (QUIC) eliminates TCP head-of-line blocking. Companies like Google, Cloudflare run HTTP/3 at scale.

3

Load Balancer

Routes request to a healthy server instance. Algorithms: Round Robin, Least Connections, IP Hash (sticky sessions), Weighted Round Robin. L4 (TCP level) vs L7 (HTTP level). L7 LBs can route by path, headers, cookies. AWS ALB, NGINX, HAProxy are common choices.

4

Server Process & Framework Routing

OS accepts connection, hands to server process (Node.js, Go, Python, Java). Framework parses HTTP, matches route (e.g., GET /api/users/:id → UsersController#show). Middleware runs in order: logging, auth, rate limiting, request parsing.

5

Application Layer Processing

Business logic runs: validate input, check authorization, apply business rules. This is where most bugs and performance issues live. Typical issues: N+1 queries, missing cache lookups, blocking I/O on event loops.

6

Database Query

Most expensive step. Connection pool leases a connection, query executes, connection returned. Slow queries add latency directly to response time. Rule of thumb: If a request hits the DB, it costs at least 1-5ms. Most API SLA targets of 100ms are spent here.

7

Response Serialization & Return

Data serialized to JSON (or Protobuf for gRPC). Response headers added (Content-Type, CORS, Cache-Control). Gzip compression applied. Response travels back through load balancer to client. Total: typically 10-500ms depending on network and workload.

Client-Server Architecture

The foundational architecture of the web. A client (browser, mobile app, service) sends requests to a server that processes them and returns responses.

✅ Advantages

  • Centralized logic and data
  • Security enforced server-side
  • Single source of truth
  • Simpler client (thin clients)
  • Easier updates — deploy once

❌ Disadvantages

  • Single point of failure
  • Network latency on every op
  • Server is the bottleneck
  • Scaling requires infrastructure
  • Offline capability is hard

Application Layers

A well-designed backend separates concerns into distinct layers. Each layer has a single responsibility and communicates only with adjacent layers.

  ┌─────────────────────────────────────────┐
  │           PRESENTATION LAYER            │
  │   HTTP Controllers · Route Handlers     │
  │   Request Parsing · Response Formatting │
  ├─────────────────────────────────────────┤
  │            SERVICE LAYER                │
  │   Business Logic · Use Cases            │
  │   Orchestration · Validation            │
  ├─────────────────────────────────────────┤
  │           REPOSITORY LAYER              │
  │   Data Access · Query Abstraction       │
  │   Caching · Connection Pooling          │
  ├─────────────────────────────────────────┤
  │           DATA LAYER                    │
  │   PostgreSQL · Redis · Elasticsearch    │
  │   Object Storage · Message Queues       │
  └─────────────────────────────────────────┘
TypeScript — Layered Architecture Example
// ─── PRESENTATION LAYER: HTTP Controller ───────────────
class UserController {
  constructor(private userService: UserService) {}

  async getUser(req: Request, res: Response) {
    const { id } = req.params;
    if (!isValidUUID(id)) return res.status(400).json({ error: 'Invalid ID' });

    const user = await this.userService.getById(id);
    if (!user) return res.status(404).json({ error: 'User not found' });

    res.json({ data: user });
  }
}

// ─── SERVICE LAYER: Business Logic ─────────────────────
class UserService {
  constructor(private userRepo: UserRepository, private cache: CacheService) {}

  async getById(id: string): Promise<User | null> {
    // Check cache first
    const cached = await this.cache.get(`user:${id}`);
    if (cached) return JSON.parse(cached);

    // Fetch from DB
    const user = await this.userRepo.findById(id);
    if (user) await this.cache.set(`user:${id}`, JSON.stringify(user), 3600);

    return user;
  }
}

// ─── REPOSITORY LAYER: Data Access ─────────────────────
class UserRepository {
  constructor(private db: Database) {}

  async findById(id: string): Promise<User | null> {
    const result = await this.db.query(
      'SELECT id, name, email, created_at FROM users WHERE id = $1',
      [id]
    );
    return result.rows[0] ?? null;
  }
}

Concurrency Models

One of the most fundamental choices in backend engineering: how does your server handle multiple requests simultaneously? This determines scalability, performance, and complexity.

ModelHow It WorksGood ForUsed By
Multi-Thread One thread per request. Thread pool. Blocking I/O is fine. CPU-bound work, simple code Java Spring, .NET, Python Django
Event Loop Single thread, non-blocking I/O, callbacks/promises I/O-bound, high concurrency Node.js, Nginx, Redis
Async/Await Cooperative multitasking within single/few threads I/O-bound, readable async code Python FastAPI, Rust Tokio, Go
Actor Model Isolated actors communicate via messages, no shared state Distributed, fault-tolerant Erlang, Akka (JVM), Elixir
Goroutines Lightweight M:N threads, scheduled by Go runtime High concurrency, low overhead Go (Kubernetes, Docker, Cloudflare)
⚠️
The Node.js Trap

Node.js runs on a single-threaded event loop. Never run CPU-intensive code (image processing, crypto, complex calculations) on the main thread — it blocks ALL incoming requests. Use worker threads or offload to a separate service.

Go — Goroutines for High Concurrency
package main

import (
    "net/http"
    "sync"
    "encoding/json"
)

// Go handles 100k+ concurrent connections easily
// Each HTTP request gets its own goroutine (~8KB stack)
// vs Java threads (~1MB stack) = 100x more concurrency

func fetchUserData(userID string) UserData {
    var wg sync.WaitGroup
    var profile Profile
    var orders []Order
    var notifications []Notification

    // Fetch all three in parallel — not sequentially!
    wg.Add(3)

    go func() {
        defer wg.Done()
        profile = getProfile(userID)
    }()

    go func() {
        defer wg.Done()
        orders = getOrders(userID)
    }()

    go func() {
        defer wg.Done()
        notifications = getNotifications(userID)
    }()

    wg.Wait() // Block until all 3 complete

    return UserData{Profile: profile, Orders: orders, Notifications: notifications}
    // Total time = max(t1, t2, t3) instead of t1 + t2 + t3
}

HTTP Deep Dive

HTTP is the backbone of web APIs. Senior engineers understand it at a protocol level, not just the surface API.

HTTP/1.1 vs HTTP/2 vs HTTP/3

  ─────────────     ─────────────         ─────────────
  req1 ─────▶       req1 ─┐               req1 ─┐
  ◀──── res1        req2 ─┤ multiplexed   req2 ─┤ over UDP
  req2 ─────▶       req3 ─┤ on 1 TCP      req3 ─┤ (QUIC)

  requests           (but TCP             head-of-line

Connection Pooling

Opening a new DB connection is expensive (~20-100ms). Connection pools maintain a set of open connections that are reused across requests.

Node.js — PostgreSQL Connection Pool
import { Pool } from 'pg';

// Configure pool — these numbers matter!
const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 20,          // Max connections in pool
  min: 5,           // Keep this many connections warm
  idleTimeoutMillis: 30000,  // Close idle connections after 30s
  connectionTimeoutMillis: 2000, // Fail fast: timeout after 2s
});

// Good: always release connections
async function getUser(id) {
  const client = await pool.connect();
  try {
    const result = await client.query('SELECT * FROM users WHERE id = $1', [id]);
    return result.rows[0];
  } finally {
    client.release(); // CRITICAL: always release, even on error
  }
}

// Better: pool.query handles acquire/release automatically
async function getUserBetter(id) {
  const { rows } = await pool.query('SELECT * FROM users WHERE id = $1', [id]);
  return rows[0];
}

// SIZING RULE: pool_size = (core_count * 2) + effective_spindle_count
// For 8-core server: 2*8 + 1 = 17 connections per app instance
// For PostgreSQL: max_connections / num_app_instances = pool_size
🔴
Connection Pool Exhaustion

If your pool of 20 connections is fully leased and a 21st request comes in, it waits (or times out). This cascades into all requests waiting → timeout storm → service appears down. Always set connectionTimeoutMillis and never hold connections across unrelated operations.

Load Balancers

A load balancer distributes incoming traffic across multiple server instances to achieve scalability and high availability.

AlgorithmHow It WorksBest ForPitfall
Round RobinRequests distributed in order: s1, s2, s3, s1...Homogeneous servers, similar request costHot servers if requests vary in cost
Least ConnectionsRoute to server with fewest active connectionsVariable processing time per requestState tracking overhead
IP HashSame client IP always hits same serverStateful apps needing sticky sessionsUneven distribution, hot servers
Weighted RRServers get requests proportional to their weightHeterogeneous server capacityRequires manual tuning
RandomPick a random serverStateless, simple, fastStatistical variance at low request counts

Health Checks

Load balancers continuously probe server health. If a server fails N consecutive checks, it's removed from rotation. This is how you achieve zero-downtime deployments and automatic failure recovery.

Python (FastAPI) — Health Check Endpoint
from fastapi import FastAPI, status
from fastapi.responses import JSONResponse
import asyncpg, redis.asyncio as aioredis

app = FastAPI()

@app.get("/health")
async def health_check():
    """
    Load balancer hits this every 5s.
    Must respond in <500ms or server is marked unhealthy.
    """
    checks = {}
    overall_healthy = True

    # Check database
    try:
        await db_pool.fetchval("SELECT 1")
        checks["database"] = "ok"
    except Exception as e:
        checks["database"] = str(e)
        overall_healthy = False

    # Check Redis
    try:
        await redis_client.ping()
        checks["redis"] = "ok"
    except Exception as e:
        checks["redis"] = str(e)
        # Redis unhealthy might be OK — depends on criticality

    http_status = status.HTTP_200_OK if overall_healthy else status.HTTP_503_SERVICE_UNAVAILABLE

    return JSONResponse(
        status_code=http_status,
        content={"status": "healthy" if overall_healthy else "unhealthy", "checks": checks}
    )

Scalability Fundamentals

🔼 Vertical Scaling (Scale Up)

  • Bigger machine (more CPU, RAM)
  • Simple — no code changes
  • Hard limit: biggest server available
  • Single point of failure remains
  • Cost: expensive at high end
  • Use when: DB primary, legacy apps

↔ Horizontal Scaling (Scale Out)

  • More machines, distribute load
  • Requires stateless app design
  • Theoretically unlimited scale
  • No single point of failure
  • Cost: linear with load
  • Use when: API servers, stateless workers
🎯
How Google Thinks About Scale

Google's SRE book defines reliability targets using error budgets: if your SLO is 99.9% uptime, you have 8.7 hours/year of allowed downtime. This budget is shared across development velocity and operations stability. When you spend your budget, you stop new features and focus on reliability.
