API Design Masterclass

APIs are the contracts between systems. A well-designed API is a joy to use; a poorly designed one haunts engineers for years. Learn REST, GraphQL, gRPC, and the principles used by Stripe, Twilio, and GitHub — APIs celebrated by developers worldwide.

⏱ 75 min read 🎯 All levels 🔌 REST · GraphQL · gRPC

REST APIs

REST (Representational State Transfer) is an architectural style defined by Roy Fielding in 2000. It's the dominant API style for web services — when in doubt, build REST.

WHY
Why REST
Simple, ubiquitous, works everywhere HTTP works, excellent tooling, easily cacheable
WHAT
What REST is
Stateless client-server architecture using HTTP methods (GET/POST/PUT/DELETE) on resources (nouns)
WHERE
Where to use REST
Public APIs, mobile backends, browser-accessible APIs, simple CRUD services
WHEN
When to choose REST
External-facing APIs, diverse clients, HTTP caching needed, simple request-response pattern

Resource Design — The Heart of REST

REST is about resources (nouns), not actions (verbs). The HTTP method IS the verb.

REST — Resource URL Design
# ✅ CORRECT — Nouns, hierarchy, plural
GET    /api/v1/users              # List users
POST   /api/v1/users              # Create user
GET    /api/v1/users/{id}         # Get specific user
PUT    /api/v1/users/{id}         # Replace user
PATCH  /api/v1/users/{id}         # Update fields
DELETE /api/v1/users/{id}         # Delete user

# Nested resources — express ownership
GET    /api/v1/users/{id}/orders  # Orders belonging to user
POST   /api/v1/users/{id}/orders  # Create order for user
GET    /api/v1/orders/{id}/items  # Items in an order

# ❌ WRONG — Verbs in URL (RPC style, not REST)
POST   /api/createUser            # Anti-pattern
GET    /api/getUser?id=123        # Anti-pattern
POST   /api/deleteUser            # Anti-pattern
GET    /api/users/fetch-all       # Anti-pattern

# ✅ Actions as sub-resources (when needed)
POST   /api/v1/orders/{id}/cancel     # Action on resource
POST   /api/v1/payments/{id}/refund   # Action on resource
POST   /api/v1/users/{id}/verify      # Trigger verification

Pagination Strategies

StrategyHow It WorksProsConsUse When
Offset/Limit ?offset=20&limit=10 Simple, random access, easy UI Slow at high offset, drift on mutations Admin UIs, small datasets
Page/Size ?page=3&size=20 Intuitive, page numbers Same offset problems User-facing paginated lists
Cursor-Based ?after=cursor&limit=20 Stable, consistent, no drift No random access, opaque cursors Feeds, infinite scroll, large datasets
Keyset ?last_id=100&limit=20 Uses index efficiently Tied to sort order, complex multi-column High-volume feeds, sorted by ID/timestamp
SQL — Cursor Pagination Implementation
-- Cursor pagination: encode cursor as base64(id)
-- Client sends: GET /users?after=eyJpZCI6IjUwIn0&limit=20
-- Server decodes cursor → {id: "50"}

-- ✅ Efficient: uses index on id
SELECT id, name, email, created_at
FROM users
WHERE id > 50    -- decoded from cursor
ORDER BY id ASC
LIMIT 21;          -- fetch one extra to detect hasNextPage

-- If 21 rows returned → hasNextPage = true, return first 20
-- Next cursor = encode(last_item.id)

-- ❌ Inefficient at scale: full table scan then skip
SELECT * FROM users ORDER BY id LIMIT 20 OFFSET 1000000;
-- PostgreSQL reads 1,000,020 rows just to return 20!

Rate Limiting

Rate limiting protects your API from abuse, ensures fair usage, and prevents accidental DDoS by misbehaving clients.

AlgorithmHow It WorksBurst HandlingMemory
Fixed Window100 req/min — counter resets every minutePoor — 200 req at window boundaryO(1)
Sliding Window LogStore timestamp of each request, count in windowExcellentO(requests)
Sliding Window CounterWeighted count from previous window + currentGood approximationO(1)
Token BucketTokens refill at rate r, consumed per requestExcellent — allows bursts up to bucket sizeO(1)
Leaky BucketQueue requests, process at fixed rateNone — smooths trafficO(queue size)
JavaScript — Token Bucket Rate Limiter (Redis)
// Redis Lua script for atomic token bucket
// Stripe uses token bucket: 100 req/s, burst up to 500
const TOKEN_BUCKET_SCRIPT = `
local key = KEYS[1]
local rate = tonumber(ARGV[1])      -- tokens per second
local capacity = tonumber(ARGV[2])  -- max burst size
local now = tonumber(ARGV[3])       -- current timestamp ms
local cost = tonumber(ARGV[4])      -- tokens this request costs

local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(bucket[1]) or capacity
local last_refill = tonumber(bucket[2]) or now

-- Calculate tokens to add since last refill
local elapsed = (now - last_refill) / 1000
local new_tokens = math.min(capacity, tokens + (elapsed * rate))

if new_tokens < cost then
  return {0, math.ceil((cost - new_tokens) / rate * 1000)}
end

new_tokens = new_tokens - cost
redis.call('HMSET', key, 'tokens', new_tokens, 'last_refill', now)
redis.call('PEXPIRE', key, math.ceil(capacity / rate * 1000))
return {1, 0}
`;

async function checkRateLimit(userId, endpoint) {
  const key = `ratelimit:${userId}:${endpoint}`;
  const [allowed, retryAfterMs] = await redis.eval(
    TOKEN_BUCKET_SCRIPT, 1, key,
    100,       // rate: 100 tokens/second
    500,       // capacity: burst up to 500
    Date.now(), // now
    1          // cost: 1 token per request
  );

  if (!allowed) {
    throw new RateLimitError({
      retryAfter: Math.ceil(retryAfterMs / 1000),
      message: `Rate limit exceeded. Retry after ${retryAfterMs}ms`
    });
  }
}

💡
Stripe's Versioning Strategy

Stripe uses date-based API versions (Stripe-Version: 2024-06-20). Each API key is locked to the version at account creation. Breaking changes create new versions. Old versions are maintained for years. This gives clients stability while letting Stripe evolve the API. This is the gold standard for API versioning.

Idempotency

An operation is idempotent if calling it multiple times has the same effect as calling it once. Critical for payment APIs, order creation, and anything where retries could cause duplicate actions.

Node.js — Idempotency Key Implementation
// Client sends unique key; server uses it to deduplicate
// POST /payments
// Idempotency-Key: payment-order-123-attempt-1

async function createPaymentIdempotent(req, res) {
  const idempotencyKey = req.headers['idempotency-key'];

  if (!idempotencyKey) {
    return res.status(400).json({ error: 'Idempotency-Key header required' });
  }

  // Check if we've seen this key before
  const cacheKey = `idempotency:${req.userId}:${idempotencyKey}`;
  const cached = await redis.get(cacheKey);

  if (cached) {
    // Return original response — DO NOT process again
    const originalResponse = JSON.parse(cached);
    res.set('Idempotent-Replayed', 'true');
    return res.status(originalResponse.statusCode).json(originalResponse.body);
  }

  // Process the payment
  const payment = await paymentService.charge(req.body);

  // Cache the response for 24 hours (typical idempotency window)
  await redis.setex(cacheKey, 86400, JSON.stringify({
    statusCode: 201,
    body: payment
  }));

  res.status(201).json(payment);
}

GraphQL

GraphQL is a query language and runtime for APIs created by Facebook (2015). It solves the over-fetching and under-fetching problems of REST by letting clients request exactly the data they need.

WHY
Why GraphQL
REST returns fixed shapes. Mobile clients need different data than desktop. Multiple round trips waste bandwidth.
WHAT
What it is
Schema-first query language. Single endpoint (/graphql). Client specifies exact fields. Strong typing.
WHEN
When to use
Multiple client types (web, mobile, TV), rapidly evolving APIs, complex nested data, teams owning different pieces

✅ GraphQL Strengths

  • Client gets exactly what it asks for
  • Single request for nested data
  • Strong schema = self-documentation
  • Real-time with subscriptions
  • Great for complex/nested domains
  • Used by: GitHub, Shopify, Twitter

❌ GraphQL Weaknesses

  • HTTP caching doesn't work (POST)
  • N+1 query problem (use DataLoader)
  • Complex queries can be expensive
  • Learning curve for teams
  • Overkill for simple CRUD APIs
  • File uploads are awkward
GraphQL — Schema & Query Example
# Schema definition
type User {
  id: ID!
  name: String!
  email: String!
  orders: [Order!]!
  createdAt: DateTime!
}

type Order {
  id: ID!
  total: Float!
  status: OrderStatus!
  items: [OrderItem!]!
}

type Query {
  user(id: ID!): User
  users(first: Int, after: String): UserConnection!
}

type Mutation {
  createUser(input: CreateUserInput!): User!
  updateUser(id: ID!, input: UpdateUserInput!): User!
}

type Subscription {
  orderStatusChanged(orderId: ID!): Order!
}

# Client query — gets exactly these fields, nothing more
query GetUserWithOrders($userId: ID!) {
  user(id: $userId) {
    id
    name
    orders {
      id
      total
      status
    }
  }
}

# Mobile app query — wants less data
query GetUserNameOnly($userId: ID!) {
  user(id: $userId) {
    id
    name
  }
}

The N+1 Problem in GraphQL

JavaScript — DataLoader for N+1 Prevention
import DataLoader from 'dataloader';

// ❌ N+1 Problem:
// Query 10 users → 1 query
// Each user.orders resolver → 10 queries
// Total: 11 queries!

// ✅ DataLoader batches and caches:
// Collects all userIds requested in same tick
// Fires ONE query: SELECT * FROM orders WHERE user_id IN (1,2,3,...)
// Returns results to each individual resolver

const orderLoader = new DataLoader(async (userIds) => {
  // Called once with ALL accumulated ids
  const orders = await db.query(
    `SELECT * FROM orders WHERE user_id = ANY($1)`,
    [userIds]
  );

  // Must return results in same order as input ids
  const ordersByUserId = groupBy(orders, 'user_id');
  return userIds.map(id => ordersByUserId[id] || []);
});

// Resolver — DataLoader deduplicates across resolver invocations
const resolvers = {
  User: {
    orders: (user) => orderLoader.load(user.id)
  }
};

gRPC

gRPC is Google's Remote Procedure Call framework built on HTTP/2 and Protocol Buffers. It's used for service-to-service communication in microservices where performance matters.

FeatureREST/JSONGraphQLgRPC
ProtocolHTTP/1.1+HTTP/1.1+HTTP/2
FormatJSON (text)JSON (text)Protobuf (binary)
PerformanceModerateModerate🚀 Excellent (5-10x faster)
StreamingLimited (SSE)SubscriptionsNative bidirectional
Type SafetyNone (manual)Schema (JS)Strong (compiled)
Browser Support✅ Native✅ Native⚠ Needs grpc-web proxy
Best ForPublic APIsComplex client needsInternal microservices
Used ByEveryoneGitHub, ShopifyGoogle, Netflix, Uber, Lyft
Protobuf — gRPC Service Definition
// user_service.proto
syntax = "proto3";
package user;

service UserService {
  // Unary RPC — one request, one response
  rpc GetUser(GetUserRequest) returns (User);

  // Server streaming — one request, stream of responses
  rpc ListUsers(ListUsersRequest) returns (stream User);

  // Client streaming — stream of requests, one response
  rpc BulkCreateUsers(stream CreateUserRequest) returns (BulkCreateResponse);

  // Bidirectional streaming — both sides stream
  rpc Chat(stream ChatMessage) returns (stream ChatMessage);
}

message User {
  string id = 1;
  string name = 2;
  string email = 3;
  int64 created_at = 4;
}

message GetUserRequest {
  string id = 1;
}

// Why Protobuf is faster than JSON:
// JSON: {"id":"abc","name":"Jane","email":"j@e.com"} = 43 bytes
// Proto: binary encoding ≈ 15 bytes (3x smaller)
// Parsing: proto ~5x faster (no string parsing)

When to Use Which API Style

Decision: REST vs GraphQL vs gRPC

Is this an external/public API?

→ YES: Do clients need very different data shapes?

→ YES: Multiple client types, complex domain → GraphQL

→ NO: Simple CRUD, diverse clients → REST

→ NO: Internal service-to-service?

→ YES: Performance critical, polyglot services → gRPC

→ NO: Internal, less critical → REST (simpler)

🎯
Netflix's API Architecture

Netflix uses all three: REST for their developer APIs, GraphQL (Falcor-inspired, then actual GraphQL) for their client-facing API gateway that serves iOS, Android, Smart TV, and web with different data shapes, and gRPC for internal microservice communication. This is the hybrid approach most large companies end up at.
